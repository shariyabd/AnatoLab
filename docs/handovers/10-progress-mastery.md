# Handover 10 — Progress, Mastery & Gamification

**Feature:** F10 · **Lane:** Progress · **Wave:** 5 · **Branch:** `feat/f10-progress-mastery`

> Read first: PRD §15, §16, §18, §29, §30 · `docs/architecture.md` §10, §13

## Objective

Turn attempts and lesson completions into a mastery score, a progress dashboard, a
recommendation, and lightweight gamification. Deliberately one feature — these share one
table, one job, and one dashboard.

## Scope

- `learning_mastery`, `learning_events`, `achievements`, `user_achievements`
- `MasteryCalculator` (pure), `ProgressService`, `RecommendationService`
- `RecalculateMastery` queued job, `POST /api/v1/events` batching endpoint
- Progress dashboard; XP, levels, badges, streaks

## Out of scope

Grading (F07/F09 decide correctness — you consume it), lesson delivery (F06), AI (F08). The
LLM never computes a score and never writes a recommendation reason.

## Dependencies / prerequisites

**F07 merged** (`attempts`) and **F06 merged** (`lesson_progress`). F07's migration lands in
its first commit, so you can start against the schema before its UI is finished.

## Existing code to reuse

None.

## Required implementation

### The formula is fixed (`docs/architecture.md` §10)

```
accuracy      = (correct_attempts + 1) / (attempts + 2)      Laplace-smoothed
recency       = exponential decay, half-life 14 days, on last_activity_at
hint_penalty  = 1 - 0.15 × (hinted_attempts / attempts)
coverage      = distinct structures attempted / structures in topic

mastery_score = 100 × accuracy × recency × hint_penalty × (0.5 + 0.5 × coverage)
```

`MasteryCalculator` is **pure** — no I/O, no persistence, no `auth()`. That makes it
table-driven testable, which is the point.

Roll up structure → organ → body system, **unweighted by attempt count**, so one heavily
drilled structure cannot carry an organ.

Recompute in `RecalculateMastery` (queued) after each attempt. **Never in the request.**

### Recommendations

Lowest-mastery published topic with unattempted content available, tie-broken toward the
current organ so the session stays coherent. Return topic, activity, and a one-line reason —
**templated from the mastery breakdown, not generated by an LLM** ("You are strong on organ
function but need practice identifying structures").

### Analytics

`learning_events` is append-only. Client-side events (`organ_viewed`, `structure_selected`,
`structure_isolated`, `layer_changed`) batch to `POST /api/v1/events` on an interval and on
page unload. Server-side events are recorded where they happen. Report learning outcomes, not
page views (PRD §30).

### Gamification

XP per completed activity, levels from XP, badges from `achievements.criteria` JSON, streaks
from `last_activity_at`. Keep it simple — **no competitive leaderboard** (PRD §16).

### API

```
GET  /api/v1/progress                  overall + recent activity
GET  /api/v1/progress/systems          per-system mastery
GET  /api/v1/progress/recommendations
POST /api/v1/events                    batched analytics
```

## Tests

- **`MasteryCalculator` table-driven**: zero attempts, all correct, all wrong, heavy hint use,
  stale activity, partial coverage. This is the highest-value test in the feature.
- Rollup: structure → organ → system, and that one structure cannot dominate
- Recalculation happens in a queued job, not the request
- Recommendation picks the weakest topic and returns a reason
- Progress scoped to `auth()->id()`
- Events endpoint rejects malformed batches and is rate limited

## Acceptance criteria

1. Answering a question visibly changes mastery.
2. Per-system percentages match PRD §15's shape.
3. A recommendation with a human-readable reason appears on the dashboard.
4. XP, level, and at least two badges work.
5. No mastery computation happens synchronously in a web request.

## Constraints and guardrails

- The formula is fixed. Changing it is an architecture change — raise it, do not improvise.
- Never cache personalised progress across users.
- Recommendation reasons are templated, never LLM-generated.
